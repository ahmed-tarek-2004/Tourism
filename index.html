V0 — the naive backend

It works. It returns JSON. So… what’s the problem?

BooksController.cs — everything, everywhere, all at once
public class BooksController : ControllerBase
{
    private readonly SqlBookRepository _repository;

    public BooksController()
    {
        // the controller creates its own dependency
        _repository = new SqlBookRepository();
    }

    [HttpPost]
    public IActionResult CreateBook(BookInput input)
    {
        // validation ... business rules ...
        // data access ... formatting ...
        // all mixed in one method
        _repository.Insert(input);
        return Ok();
    }
}

It runs

V0 is a working system. That matters — we always start from working software.

But change is expensive

Swap SQL for anything else? Test the business rule alone? Every change touches this one class.

The real problem: dependency direction

Business logic
↓ depends on
SqlBookRepository a concrete infrastructure detail

The most important code in the system
is chained to the most replaceable code.

SymptomCause
Can’t unit testDependency is hard-wired with new
Can’t swap the databaseBusiness code names a concrete class
Every change ripplesNo boundaries — one class, many reasons to change
Fear of refactoringNo seams to isolate behavior

The fix is a concept, not a framework: control which way dependencies point.

Clean & Onion Architecture

Two closely related architectural styles.
Both share one core rule:

Dependencies point inward.
The core (business logic) knows nothing about the outside (infrastructure, web, database).

  • Domain sits at the center — pure business model
  • Application orchestrates use cases around it
  • Infrastructure & API live at the edge — replaceable details
Common misconceptions — let’s kill them early

Related is not equal

✕ “Clean = Onion”

They are closely related styles with different histories and vocabulary. Both protect the core via inward dependencies — but they are not the same thing.

✕ “Clean Architecture requires CQRS”

It doesn’t. Neither does Onion. You can build a fully clean/onion system with plain services and no CQRS at all.

✕ “CQRS is part of the architecture”

CQRS is a separate design pattern. It can be applied inside Clean, inside Onion — or inside neither.

Architecture styles answer “which way do dependencies point?” — CQRS answers “should reads and writes share one model?” Different questions. Composable answers.

Concept · SOLID — the “D”

Dependency Inversion Principle

BAD — high-level code depends on a concrete class
public class UserService
{
    private readonly SqlUserRepository _repository;

    public UserService()
    {
        _repository = new SqlUserRepository();
    }
}

UserService names and creates its dependency. It is welded to SQL forever.

High-level code should depend on abstractions —
not concrete implementations.

UserService high-level policy
↓ depends on
IUserRepository abstraction
↑ implements
SqlUserRepository low-level detail

The detail now depends on the abstraction. The arrow got inverted — hence the name.

Refactor: introduce the abstraction

the abstraction + the detail
public interface IUserRepository
{
    string GetUserName(int id);
}

public class SqlUserRepository : IUserRepository
{
    public string GetUserName(int id)
    {
        return $"SQL User - {id}";
    }
}
the high-level class — now DIP-compliant
public class UserService
{
    private readonly IUserRepository _repository;

    public UserService(IUserRepository repository)
    {
        _repository = repository;
    }
}

UserService no longer knows which repository exists. Swap SQL → InMemory → Mongo: zero changes here.

But someone still has to create the concrete object and pass it in. Who?

Technique

Dependency Injection — supply dependencies from outside

manual DI — no framework, no magic
IUserRepository repository =
    new SqlUserRepository();

var service = new UserService(repository);

This is dependency injection. Two lines. No container, no library, no attribute.

DIP ≠ DI

DIP is a design principle: what to depend on (abstractions).

DI is a technique: how dependencies arrive (from outside, usually via the constructor).

And DI does not require a container

The code on the left injects dependencies with plain new. A container is a convenience we add next — not a prerequisite.

Tool · framework mechanism

The .NET DI Container — automate the wiring

register once…
services.AddScoped<IUserRepository,
                   SqlUserRepository>();
services.AddScoped<UserService>();

var provider = services.BuildServiceProvider();
…resolve anywhere
var userService =
    provider.GetRequiredService<UserService>();

// container built SqlUserRepository,
// injected it into UserService,
// and handed us the finished object graph

Manually new-ing 3 objects is fine. 300 objects with lifetimes? That’s what the container automates.

What the container actually does

1  BuildServiceProvider() — freeze the recipe book

Service asked forBuild recipeLifetime
IUserRepositorynew SqlUserRepository()Scoped
UserServicenew UserService(resolve(IUserRepository))Scoped

2  GetRequiredService<UserService>() — walk the graph

↓

↓

↓

Recursive constructor resolution + lifetime management. No magic — just automated manual DI.

Three different things — keep them separate

Principle

DIP

“Depend on abstractions.”

A design rule. Exists on paper — no code required.

Technique

DI

“Provide dependencies from outside.”

A way of constructing objects. Works with plain new.

Tool

DI Container

“Automate dependency resolution.”

A framework mechanism: registrations, lifetimes, object graphs.

DIP tells us what
→
DI tells us how
→
The container does it at scale

Applying it: the repository abstraction

Application · owns the abstraction it needs
public interface IBookRepository
{
    Task<Book?> GetByIdAsync(
        Guid id,
        CancellationToken cancellationToken);
}
Application · the service depends on it
public class BookService
{
    private readonly IBookRepository _repository;

    public BookService(IBookRepository repository)
    {
        _repository = repository;
    }
}
Infrastructure · provides the implementation
public class InMemoryBookRepository : IBookRepository
{
    public Task<Book?> GetByIdAsync(
        Guid id,
        CancellationToken cancellationToken)
    {
        var book = new Book(
            id,
            "Clean Architecture");

        return Task.FromResult<Book?>(book);
    }
}

The Application layer owns the abstraction it needs.
Infrastructure provides the implementation.

Guardrail

The Repository Pattern doesn’t dictate
where the interface lives

The pattern says

“Put an abstraction between business logic and data access.”

That’s all. Nothing about folders, projects, or namespaces.

The architecture decides placement

Because our dependencies point inward, the interface lives in Application — the layer that needs it — and the implementation lives at the edge.

Different architecture → possibly a different placement. The dependency direction is the reason, not the pattern.

Application defines IBookRepository
←
Infrastructure implements InMemoryBookRepository
←
API wires them in Program.cs

The service that does everything

BookService.cs — six months later
public class BookService
{
    public Task CreateBook(...)   { }
    public Task UpdateBook(...)   { }
    public Task DeleteBook(...)   { }

    public Task<Book?>      GetBook(...)     { }
    public Task<List<Book>> GetBooks(...)    { }
    public Task<List<Book>> SearchBooks(...) { }

Two very different jobs, one class

Writes need validation, rules, transactions.
Reads need speed, shaping, filtering, paging.

They change for different reasons, at different speeds, with different performance profiles — yet they share one model and one class that keeps growing.

The concept: separate intent

Commands — change state
CreateBook
UpdateBook
DeleteBook

Validated. Authorized. Transactional. Return little or nothing.

Queries — read state
GetBook
GetBooks
SearchBooks

Side-effect free. Shaped for the caller. Optimizable independently.

CQRS — Command Query Responsibility Segregation: give writes and reads separate paths, so each can evolve on its own terms.

Guardrail

CQRS does not mean two databases

What CQRS requires

Separate code paths for commands and queries. That’s the whole contract.

Commands
→
one database
←
Queries

Our Library System: one store, two paths. Fully CQRS.

What’s optional (and advanced)

Separate read/write stores, replicas, projections, event sourcing — possible extensions, each with heavy consistency trade-offs.

Don’t pay that cost until a real problem demands it. We won’t.

Start with the simplest CQRS that solves today’s problem: separated handlers over one store.

How do requests find their handler?

Mediator pattern

A communication pattern: senders hand a request to a mediator, which routes it to exactly one handler. Sender and handler never know each other.

Why it fits CQRS

The endpoint doesn’t call BookService anymore. It dispatches CreateBookCommand — and the matching handler picks it up. One request type → one handler → one responsibility.

Controller / Endpoint knows only the request type
↓ send(request)
Mediator routes by type
↓
Command / Query Handler one class, one use case
↓
Application logic repositories, domain, rules
Implementation · MediatR

The write path: CreateBook

Application/Commands/Books/CreateBook
public record CreateBookCommand(
    Guid Id,
    string Title
) : IRequest<Guid>;

The command is a message — immutable data describing intent. IRequest<Guid> declares what it returns.

its one and only handler
public class CreateBookHandler
    : IRequestHandler<CreateBookCommand, Guid>
{
    private readonly IBookRepository _repository;

    public CreateBookHandler(IBookRepository repository)
    {
        _repository = repository;
    }

    public async Task<Guid> Handle(
        CreateBookCommand request,
        CancellationToken cancellationToken)
    {
        var book = new Book(request.Id, request.Title);

        await _repository.AddAsync(book, cancellationToken);

        return book.Id;
    }
}

The read path: GetBook

Application/Queries/Books/GetBook
public record GetBookQuery(
    Guid Id
) : IRequest<Book?>;

public class GetBookHandler
    : IRequestHandler<GetBookQuery, Book?>
{
    private readonly IBookRepository _repository;

    public GetBookHandler(IBookRepository repository)
    {
        _repository = repository;
    }

    public async Task<Book?> Handle(
        GetBookQuery request,
        CancellationToken cancellationToken)
    {
        return await _repository.GetByIdAsync(
            request.Id, cancellationToken);
    }
}
API/Program.cs — the endpoint just dispatches
app.MapGet("/books/{id:guid}",
    async (
        Guid id,
        ISender sender,
        CancellationToken cancellationToken) =>
    {
        var query = new GetBookQuery(id);

        var book = await sender.Send(
            query, cancellationToken);

        return book is null
            ? Results.NotFound()
            : Results.Ok(book);
    });

The endpoint knows no service, no repository — only the query type and the mediator.

Composition root: everything meets in Program.cs

var builder = WebApplication.CreateBuilder(args);

// abstraction → implementation
builder.Services
    .AddSingleton<IBookRepository,
                  InMemoryBookRepository>();

// discover all handlers in Application
builder.Services.AddMediatR(config =>
    config.RegisterServicesFromAssembly(
        typeof(CreateBookCommand).Assembly));

var app = builder.Build();

$ dotnet add LibrarySystem.Application \

$ dotnet add LibrarySystem.API \

Note the lifetime choice

Singleton fits an in-memory list that must survive across requests. When EF Core arrives in Session 2, this becomes Scoped — lifetimes are a decision, not a default.

Guardrail

CQRS ≠ Mediator ≠ MediatR

Design pattern

CQRS

Separate the responsibility for reads and writes.

Achievable with plain classes — no mediator needed.

Communication pattern

Mediator

Decouple senders from receivers through a middleman.

Useful far beyond CQRS.

.NET library

MediatR

One popular implementation of mediator-style request handling.

A tool we chose — not the concept itself.

We use MediatR to implement CQRS conveniently.
Delete the library tomorrow — the pattern and the principle survive.

Concept · before any tool

Why do applications log?

Why logs exist the system must explain itself after the fact
↓
What should be logged requests · business events · failures
↓
Structured logging properties, not sentences — machines query logs
↓
Levels Debug · Information · Warning · Error
unstructured — a sentence you can only read
"Book 4f2a… created by member 812 in 34ms"
structured — data you can query
{
  "Message": "Book created",
  "BookId": "4f2a…",
  "MemberId": 812,
  "ElapsedMs": 34,
  "Level": "Information"
}

“Show me every failed checkout for member 812 this week” — only possible when log events carry structured properties.

Tool · implementation

Serilog — our logging implementation

API/Program.cs — plug Serilog in once
builder.Host.UseSerilog((context, config) =>
    config
        .ReadFrom.Configuration(context.Configuration)
        .Enrich.FromLogContext()
        .WriteTo.Console());

// log every HTTP request as one structured event
app.UseSerilogRequestLogging();
$ dotnet add LibrarySystem.API \
    package Serilog.AspNetCore
handlers log through the abstraction
public class CreateBookHandler
    : IRequestHandler<CreateBookCommand, Guid>
{
    private readonly IBookRepository _repository;
    private readonly ILogger<CreateBookHandler> _logger;

    public async Task<Guid> Handle(
        CreateBookCommand request,
        CancellationToken cancellationToken)
    {
        var book = new Book(request.Id, request.Title);
        await _repository.AddAsync(book, cancellationToken);

        // business event, structured properties
        _logger.LogInformation(
            "Book {BookId} created with title {Title}",
            book.Id, book.Title);

        return book.Id;
    }
}
